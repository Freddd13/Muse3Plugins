# 实现原理与钢琴扩展路线

## 用通俗的话理解

它是一个“能听懂结构化命令的乐谱遥控器”。Codex 理解自然语言请求，Python 服务把工具调用翻译为 JSON，例如“第 3 小节”“加入 MIDI 60 的四分音符”；MuseScore 内的 QML 插件用原生 API 操作当前乐谱，再把结果发回。MCP 不是音乐识别算法，也不会自动打开/保存乐谱；音乐判断由 AI 或后续专门算法完成。

```text
用户请求 → Codex + skill → MCP stdio → server.py / src/tools
                                      ↓
                       MuseScoreClient / 单连接、串行请求
                                      ↓ WebSocket 127.0.0.1:8765
                       musescore-mcp-websocket.qml / QtWebSockets
                                      ↓
                       MuseScore 3 Evolution 的当前乐谱
```

`src/tools` 按连接、导航、音符/小节、谱表、时间、批处理和查看器分模块。`src/types/action_types.py` 描述批处理参数。读谱遍历小节、谱表和四个声部，以 tick 表示时间。四分音符 480 tick；小节必须沿真实边界判断，不能总按 1920 tick 推算，因为弱起、变拍与连音会改变实际结构。

QML 返回 `{status:"success",result:...}`；内层仍可能有 `error`，因此不能把外层 success 当作写入成功。写操作通常使用 MuseScore startCmd/endCmd，保留原生撤销。批处理逐项执行，失败停止但前面成功的项不会整体回滚。WebSocket 无请求 ID，所以 Python 必须串行匹配发送与接收；写入后连接中断时不能自动重复命令。

## 实际支持的能力

| 类别 | 当前实现 | 注意事项 |
| --- | --- | --- |
| 读谱 | 标题、小节边界、谱表、四声部、MIDI/TPC 拼写、实际/书面时值、歌词、逐音延音、tuning、veloType/veloOffset | 结构化 JSON 是分析依据；力度偏移不等于最终渲染 MIDI 力度 |
| 选区与导航 | 起点/终点、小节、前后元素/谱表、自定义 tick 范围 | 选区/导航会改变用户选择；读整谱不改变选择 |
| 创作 | 音符、叠加和弦、休止、连音、歌词、添加乐器 | 原生自动规范时值可能拆成延音链，写后须读回 |
| 乐谱编辑 | 插入/追加小节、删除选择、拍号、速度、撤销、批处理 | 跨小节/复调/连音等复杂编辑需要实际谱验证 |
| 谱面预览 | 保留 show_score 的 VexFlow MCP App 和 get_score 的 LilyPond 文本 | VexFlow 无延音线和连音括号，拍号/布局近似；不是原生排版截图 |
| 谱表/音色 | 保留原接口 | set_staff_mute 原代码意在修改可见性，但 MS3 无该属性，本轮明确报不支持；set_instrument_sound 只打开人工选择对话框 |

尚无直接 MCP 工具写入指法、踏板曲线、力度曲线、SF2、Mixer、调律、版面样式或导出。QML 能读到的属性不等于已经封装了可用的工具。原 README 中 `set_title`、`add_lyrics_to_current_note` 也未注册，不能照示例调用。

| 软件已有功能 | 对 MCP 的影响 | 最优路径 |
| --- | --- | --- |

| 0.9–0.11 力度/速度/踏板编辑器、试听、选音和停播提交 | 不宜在播放时从插件绕开暂存/渲染边界；原生 MIDI 力度有基准/模式换算 | 先只读分析，停播写原生属性；需要最终力度或播放中预览时再评估最小只读/批量 API |

原插件引用的 `api.websocketserver` 在本软件源码中不存在；安装包含 QtWebSockets QML 模块，本轮改为 Qt 自带服务器并补齐匹配 DLL。无需重新编译软件本体。使用 `get_capabilities` 报告应用版本、桥版本和观察器可用性，不能仅以上游版本 3.7.0 推断个人功能版本。

## 钢琴场景的可行性与优先级

| 场景 | 现在可以做什么 | 推荐增量实现 |
| --- | --- | --- |
| 钢琴分析 | 结构化读谱后检查音域、手跨度、声部进行、节奏密度与候选和声；给小节/谱表/声部/tick 定位 | 优先加入分段读取、稳定音符地址、调号/拍号/力度/踏板上下文；确定性算法生成候选，AI 解释歧义 |
| 提示 | 给文字建议 | 复用 ScoreObserver 临时颜色/标签与 HarmonyAssistant 的上下文；提示不产生谱面撤销，实时显示留在本地插件，不逐帧调用 AI |
| 调音/演奏润色 | 当前可设速度、读存储力度/cent 偏移，生成乐句建议 | 如果“调音”指听感，增加停播批量力度/速度/踏板 patch，沿用原属性及 undo；调律另需 tuning 写工具。物理钢琴调音/麦克风测频不在现有链路中 |
| 净书 | 检查并提出休止/延音/分组/声部建议，做已有工具覆盖的改写 | 补充指法、连线、踏板、连梁、断行与样式的定向工具，先有作用域和差异预览，再一次撤销写入；最终用原生 PDF/谱面验证 |

先建立“可靠读取 → 明确建议 → 小范围修改 → 原生核验”，比把通用任意 QML 执行开放给 AI 更容易维护。音乐语义优先放 Python 算法层，当前上下文/屏幕提示放 QML，已有原生演奏与渲染边界继续由软件负责。只有插件确实无法获得最终力度、安全播放边界或批量性能不足时，才增加小而通用的原生 API，并按 AGENTS.md 记录版本、开发日志、用户指南及提交。

## 本轮已执行的计划

1. 同步代码、对照个人指南/最近提交，创建独立 Codex 分支。
2. 替换不存在的 WebSocket 宿主接口，增加能力探测和准确的分析字段。
3. 保留现有工具，修复响应解包，增加 get_score_data 与 set_tempo，补齐 setTempo 批处理类型。
4. 防并发错配、超时与重复写入，修复批处理失败反馈、单谱表自定义选区及撤销事务。
5. 更新 Codex skill、安装脚本、中文文档和软件用户指南，进行 MCP/mock 与实际 MuseScore 宿主测试。

后续演奏写入、临时提示及净书接口属于下一轮功能扩展，本轮没有宣称它们已实现。

## P2 当前谱与编配建议

`src/context/service.py`管理独立任务和资料，`src/tools/arrangement.py`提供MCP入口；QML桥转发到原生ScoreObserver的分批查询与候选处理。参数和完整操作见[P2接口说明](P2_CONTEXT_API.md)。
